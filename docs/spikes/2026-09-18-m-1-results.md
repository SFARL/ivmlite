## 探针环境

- **cdylib**: 一次性 Rust crate，`rustc 1.95.0` / `cargo 1.95.0`，依赖 `rusqlite = "0.40.2"`（features: `loadable_extension`, `vtab`, `functions`），`libsqlite3-sys 0.38.2`（自动解析）。代码位于会话 scratchpad `m1-spike/`，**不在本仓库内，不进 workspace，不提交**。
- **加载路径**: `/opt/homebrew/opt/sqlite/bin/sqlite3`（3.53.0，`OMIT_LOAD_EXTENSION` = 0）。矩阵全部结果都在这个 sqlite3 build 上取得，除非另行说明。
- **方案 A 实现**: 标量 UDF `ivm_create_view(name, base_table)` / `ivm_refresh(name)`。函数体内通过 `Context::get_connection()`（`sqlite3_context_db_handle`）拿到当前连接，在其上执行 `CREATE TABLE` + `CREATE TRIGGER` + `INSERT`——即在一条正在 `sqlite3_step()` 的语句内部递归使用同一连接。
- **方案 B 实现**: 虚表模块 `ivm`（`Module::update_module()`，非 eponymous，可写）。`xCreate` 用 `VTabConnection::handle()` 拿到发起 `CREATE VIRTUAL TABLE` 的连接，在其上建影子表 `<name>_data`、trigger `<name>_trig`，并写入一行 bootstrap 记录；`declare_vtab` 声明单列表 `<name>`，与 FTS5 惯用法一致。`xUpdate`（`INSERT INTO v(v) VALUES('refresh')`）向影子表追加一行；`xDestroy` 先删 trigger 再删影子表；`xFilter`/`xColumn` 读影子表内容回放给 `SELECT * FROM v`。

**双方都不做真实的增量维护，只探测机制。**

## 场景 8 详情：DDL 安全，自写扫描表灾难性失控

矩阵要求单独展开这一格，因为它的两个子情况结果截然不同。

**子情况一：对正被扫描的表做 DDL。**

```sql
SELECT id,
       CASE WHEN id = 3 THEN ivm_create_view('v8e', 'orders') ELSE 'skip' END
FROM orders ORDER BY id;
```

即"建视图"的 DDL 目标就是外层 `SELECT` 正在扫描的表本身（`orders`），无论触发点在首行、中间行还是末行，扫描都完整跑完、无报错，`PRAGMA integrity_check` 之后仍为 `ok`。这比探针文档预期的"很可能是 A 最先出问题的一格"更乐观——但只在这一个具体形状上成立：单条即席语句（非缓存的、跨多次调用复用的 prepared statement），且 schema 变更是"新增"（建新表、新 trigger），不改动 `orders` 自身的列布局或 root page。**不能从这一格结果外推到"A 对被扫描表做 DDL 总是安全"**——SQLite 的 schema-cookie 校验发生在语句开始 `sqlite3_step` 时，这次探测没有触碰到那条边界，不代表边界不存在。

**子情况二：对正被扫描的表本身做写入（自引用）。**

```sql
SELECT ivm_create_view('v8g', 'orders');
SELECT seq, ivm_refresh('v8g') FROM shadow_a_v8g;   -- 扫描 shadow_a_v8g 的同时 ivm_refresh 又在写它
```

**这个失控了。** `ivm_refresh` 每处理一行就往 `shadow_a_v8g` 追加一行，而外层 `SELECT` 的表扫描游标没有快照隔离,新追加的行立刻被同一个游标看到、再次触发调用——变成自我喂养式的无界循环。实测到 464,538 行时手动杀掉进程，此前没有任何错误、没有变慢的迹象，会一直跑到磁盘或内存耗尽为止。这不是"报错"或"未定义行为"这种温和说法能覆盖的——**是一个真实的、可复现的资源耗尽故障**，比预期的失败形态更糟。

现实中 `ivm_refresh('v')` 的自然调用形式是裸的顶层语句（`SELECT ivm_refresh('v');`），不会写成 `SELECT ivm_refresh('v') FROM v_shadow`；但这次探测证明了：**方案 A 的控制面没有任何机制阻止用户写出这种自引用调用**，一旦写出就是这种量级的故障，而不是一个容易发现的报错。这是本次探针中方案 A 最严重的问题，比场景 9 的悬空 trigger 更危险，因为场景 9 至少会立刻报错，这个不会。

方案 B 结构上不暴露同等风险：读路径（`SELECT * FROM v` → `xFilter`/`xColumn`）不执行任何写入；写路径（`INSERT INTO v(v) VALUES('refresh')` → `xUpdate`）是一条独立语句，不是从"正在扫描某表的回调"里发起的。这是架构论证，**未在本次矩阵中对 B 实测**（矩阵把场景 8 定义为 A 独有），如实标注为未实测但有结构性理由。

## 场景 3 / 4 对 §7.3 bootstrap 原子性论证的意义

在真实 cdylib 上下文重新验证：**DDL 是事务性的，两套方案都是。** `ROLLBACK` 与 `SAVEPOINT ... ROLLBACK TO` 都让影子表与 trigger 随事务一并消失，不留孤儿对象。

**结论：§7.3 的 bootstrap 原子性论证不需要重写。** "建视图"这个操作（建影子表 + 建 trigger + 灌 bootstrap 状态）可以包在一个事务里，失败时干净回滚，不留半成品——无论走 A 还是走 B。

## 场景 6 / 7：并发行为是 SQLite 标准语义,两套方案没有差异

两套方案在并发场景下的行为完全对称，符合 SQLite 教科书式的锁语义,没有出现任何一方独有的问题：

- **rollback-journal 模式**：无论连接 B 在读（`BEGIN; SELECT`）还是在写（`BEGIN IMMEDIATE; INSERT`）,连接 A 调用控制面都立即拿到 `SQLITE_BUSY`（探针里 `busy_timeout=0`，所以是立即失败而不是等待）。
- **WAL 模式**：连接 B 在读时,连接 A 的控制面调用不被阻塞、立即成功（WAL 读不挡写）；连接 B 在写时,连接 A 拿到 `SQLITE_BUSY`（WAL 下写者互斥）。

这两格没有为方案选型提供信号——两套方案都只是在做普通的 DDL/DML,SQLite 的锁管理器不区分调用来自标量函数还是虚表方法。真正的信号来自场景 8 和场景 9。

## macOS 系统 `sqlite3` 无法加载扩展——对交付形态的影响

`/usr/bin/sqlite3`（macOS 自带，3.51.0）是用 `SQLITE_OMIT_LOAD_EXTENSION` 编译的，`.load` 命令不存在，`load_extension()` 函数也不存在（本次验证：直接报 `no such function: load_extension`）。本次探针全程改用 `/opt/homebrew/opt/sqlite/bin/sqlite3`（3.53.0）加载 cdylib。

spec §3 已经明确 v0 形态是"SQLite loadable extension（Rust cdylib）",并声明不覆盖浏览器与 iOS 系统 SQLite。这次验证补充一条同类的事实：**苹果自己发行的 macOS 系统 sqlite3 CLI 同样不可用作 ivmlite 的宿主**——这不影响 v0 形态的选择（cdylib 仍然是对的形态，覆盖 server/桌面/CLI 的说法仍然成立），但意味着：

1. **"CLI 好上手" 的演示路径在 macOS 上不能用系统自带的 `sqlite3`**,必须让用户装 homebrew 版本（或任何非 Apple 发行、未关闭 load extension 的 build）,这是一条文档/onboarding 层面需要写清楚的坑,不是架构问题。
2. 大多数语言绑定（Python 的 `sqlite3` 模块、`rusqlite` 本身、DB Browser for SQLite 等）链接的不是 Apple 系统那份 libsqlite3,默认没有关掉 load extension,所以"应用内嵌入使用"这条路径不受影响。
3. 这条事实**不需要改 §3**,只是补充说明,建议在用户文档/README 里提前写明"如果你在 macOS 上用系统自带 sqlite3 CLI,`.load` 会失败,换 homebrew 版本"。

## 决策

**方案 B 在所有适用于它的场景上全绿**（场景 8 按矩阵定义不适用于 B）。按探针文档的决策规则："B 全绿 → 采用 B,§8.3 定稿,控制面语法固定为 `CREATE VIRTUAL TABLE ... USING ivm(...)`"。

方案 A 并非全绿：场景 8 的自引用写入是一次严重的、无提示的资源耗尽故障；场景 9 的悬空 trigger 会把用户的基表写死,且没有配套的销毁 API 能像 `xDestroy` 一样由 SQLite 驱动、顺序正确地清理。这两条**不是决定性的**（决策规则里唯一会导致"停下不进 M1"的是两套方案都有问题,这里不是那种情况）,但足以确认"仍选 B"这一档——即便不追究 A 的问题,B 本身三处结构优势（DDL 在设计好的上下文里发生、视图是 `sqlite_master` 认识的真实对象、`DROP TABLE` 走 `xDestroy` 自然清理）依然成立,场景 8/9 的实测只是让这个选择的证据更充分。

**A 作为备选记录，但不建议在 v0 采用**：如果将来出于某种原因需要退回到标量 UDF 形态,场景 8/9 的两个坑必须先被解决——场景 9 需要一个显式销毁 API 并保证调用顺序,场景 8 需要在文档或运行时层面明确禁止"在扫描目标影子表的语句里调用 refresh"这类自引用形状,否则会遇到这次实测到的无界循环。
