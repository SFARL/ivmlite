## 已验证

这几格只涉及 SQLite 自身对 DDL 与 trigger 的处理，与控制面选型无关，因此先用 stock `sqlite3` CLI 直接验证。

### 场景 3 / 4：DDL 是事务性的 ✅

```sql
BEGIN;
  CREATE TABLE shadow(...);
  CREATE TRIGGER t_ins AFTER INSERT ON orders BEGIN ... END;
ROLLBACK;
-- sqlite_master 中无遗留：shadow 与 t_ins 都消失
```

`SAVEPOINT` + `ROLLBACK TO` 同样回滚 DDL。

**对 §7.3 的意义**：bootstrap 的原子性论证成立。"读高水位 + 扫基表 + 置 progress"可以包在一个事务里，失败时不留半成品。建视图这个操作本身也可以做成事务性的——建影子表、建 trigger、灌初始状态要么全成要么全不成。

### 场景 9：`DROP TABLE` 不清理指向它的 trigger ❌ —— 这是个有杀伤力的坑

```sql
CREATE TABLE shadow3(...);
CREATE TRIGGER t3_on_orders AFTER INSERT ON orders BEGIN
    INSERT INTO shadow3 ...;
END;

DROP TABLE shadow3;
-- t3_on_orders 仍在 sqlite_master 中

INSERT INTO orders VALUES (1,'a',10);
-- Error: no such table: main.shadow3
```

**trigger 建在基表上，影子表只是它的写入目标**，所以删影子表不会连带删 trigger。悬空的 trigger 随后会**让用户自己的基表写不进去**——爆炸半径不在视图，而在用户的数据表。

这条有三个直接后果：

1. **销毁必须先删 trigger、再删影子表，且必须在一个事务内**（场景 3 已证明事务性可用）。
2. **这显著加重了 §8.3 选方案 B 的理由。** 标量 UDF 方案需要用户记得调用 `ivm_drop_view()`；一旦忘记、或中途失败，基表就被毒死了。虚表方案下 `DROP TABLE revenue` 走 xDestroy，销毁顺序由扩展掌握，且是 SQLite 自己驱动的路径。
3. **需要一个自检/修复入口**：库里已经存在悬空 trigger 时（用户手工 `DROP` 了影子表、或旧版本留下的残骸），要能检测并清理，而不是让基表一直写不进去。这一条 spec 里目前没有，M1 要补。

### 已有的初步信号

在宿主语言的 sqlite3 绑定里，UDF 内部 `CREATE TABLE` 与 `INSERT`（含写正在被扫描的表）都没有报错。**这不清账**——不是 cdylib 路径，且没覆盖 rollback / WAL / 双连接。

同时确认 FTS5 的惯用法可用：`CREATE VIRTUAL TABLE docs USING fts5(body)` 经 xCreate 建出 `docs_data` / `docs_idx` / `docs_content` / `docs_docsize` / `docs_config` 五张影子表，`INSERT INTO docs(docs) VALUES('rebuild')` 命令通道成功。
