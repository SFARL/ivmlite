## Probe environment

- **cdylib**: a throwaway Rust crate, `rustc 1.95.0` / `cargo 1.95.0`, depending on `rusqlite = "0.40.2"` (features `loadable_extension`, `vtab`, `functions`) and `libsqlite3-sys 0.38.2` (resolved automatically). The code lived in the session scratchpad under `m1-spike/` — **not in this repository, not in the workspace, never committed**.
- **Loader**: `/opt/homebrew/opt/sqlite/bin/sqlite3` (3.53.0, `OMIT_LOAD_EXTENSION` = 0). Every result in the matrix was obtained on this sqlite3 build unless stated otherwise.
- **Design A implementation**: scalar UDFs `ivm_create_view(name, base_table)` / `ivm_refresh(name)`. The function body obtains the current connection through `Context::get_connection()` (`sqlite3_context_db_handle`) and runs `CREATE TABLE` + `CREATE TRIGGER` + `INSERT` on it — that is, it re-enters the same connection from inside a statement that is mid-`sqlite3_step()`.
- **Design B implementation**: a virtual-table module `ivm` (`Module::update_module()`, not eponymous, writable). `xCreate` obtains the connection issuing `CREATE VIRTUAL TABLE` through `VTabConnection::handle()`, creates the shadow table `<name>_data` and the trigger `<name>_trig` on it, and writes one bootstrap row; `declare_vtab` declares a single-column table `<name>`, matching the FTS5 idiom. `xUpdate` (`INSERT INTO v(v) VALUES('refresh')`) appends a row to the shadow table; `xDestroy` drops the trigger first, then the shadow table; `xFilter` / `xColumn` read the shadow table back for `SELECT * FROM v`.

**Neither design does real incremental maintenance; they only probe the mechanism.**

## Scenario 8 in detail: DDL is safe, writing to the scanned table runs away catastrophically

The matrix calls for this cell to be expanded on its own, because its two sub-cases come out completely differently.

**Sub-case one: DDL on the table being scanned.**

```sql
SELECT id,
       CASE WHEN id = 3 THEN ivm_create_view('v8e', 'orders') ELSE 'skip' END
FROM orders ORDER BY id;
```

Here the target of the view-creating DDL is the very table the outer `SELECT` is scanning (`orders`). Whether the call fires on the first row, a middle row, or the last, the scan completes without error, and `PRAGMA integrity_check` still reports `ok` afterwards. That is more optimistic than the probe document's expectation that this was "most likely where A fails first" — but it holds only for this one concrete shape: a single ad-hoc statement (not a cached prepared statement reused across calls), and a schema change that only *adds* (a new table, a new trigger) without altering `orders`' own column layout or root page. **This cell cannot be extrapolated to "DDL on a scanned table is always safe under A"**: SQLite's schema-cookie check happens when a statement starts `sqlite3_step`, this probe never touched that boundary, and not touching it does not mean it is not there.

**Sub-case two: writing to the table being scanned (self-reference).**

```sql
SELECT ivm_create_view('v8g', 'orders');
SELECT seq, ivm_refresh('v8g') FROM shadow_a_v8g;   -- ivm_refresh writes shadow_a_v8g while it is being scanned
```

**This one ran away.** Each row `ivm_refresh` processes appends a row to `shadow_a_v8g`, and the outer `SELECT`'s table-scan cursor has no snapshot isolation, so the newly appended row is immediately seen by the same cursor and fires another call — a self-feeding, unbounded loop. The process was killed by hand at 464,538 rows; until then there was no error and no sign of slowing down, and it would have run until disk or memory ran out. Mild phrasing like "an error" or "undefined behaviour" does not cover it: **this is a real, reproducible resource-exhaustion failure**, worse than the failure mode anticipated.

In practice the natural form of `ivm_refresh('v')` is a bare top-level statement (`SELECT ivm_refresh('v');`), not `SELECT ivm_refresh('v') FROM v_shadow`. But the probe shows that **design A's control surface has no mechanism at all to stop a user from writing this self-referential call**, and once written, the failure is of this magnitude rather than an easy-to-spot error. It is design A's most serious problem in this probe, more dangerous than scenario 9's dangling trigger, because scenario 9 at least fails immediately with an error and this does not.

Design B does not expose an equivalent risk, structurally: the read path (`SELECT * FROM v` → `xFilter` / `xColumn`) performs no writes, and the write path (`INSERT INTO v(v) VALUES('refresh')` → `xUpdate`) is a standalone statement, not something started from a callback inside a scan of some table. That is an architectural argument; **B was not measured on this in the matrix** (which defines scenario 8 as A only), and it is recorded as unmeasured but structurally motivated.

## What scenarios 3 and 4 mean for §7.3's bootstrap-atomicity argument

Re-verified in a real cdylib context: **DDL is transactional, under both designs.** `ROLLBACK` and `SAVEPOINT ... ROLLBACK TO` both make the shadow table and the trigger disappear along with the transaction, leaving no orphans.

**Conclusion: §7.3's bootstrap-atomicity argument does not need to be rewritten.** The "create a view" operation (create the shadow table + create the trigger + load the bootstrap state) can be wrapped in one transaction and rolled back cleanly on failure, leaving nothing half-built — whether through A or B.

## Scenarios 6 and 7: concurrency is standard SQLite semantics, with no difference between the designs

The two designs behave exactly symmetrically under concurrency, following textbook SQLite locking; neither shows a problem of its own:

- **Rollback-journal mode**: whether connection B is reading (`BEGIN; SELECT`) or writing (`BEGIN IMMEDIATE; INSERT`), connection A's control-surface call gets `SQLITE_BUSY` immediately (the probe used `busy_timeout=0`, so it fails at once rather than waiting).
- **WAL mode**: while connection B reads, connection A's control-surface call is not blocked and succeeds immediately (WAL readers do not block writers); while B writes, A gets `SQLITE_BUSY` (WAL writers are mutually exclusive).

These two cells give no signal for choosing a design: both designs just run ordinary DDL/DML, and SQLite's lock manager does not distinguish whether a call came from a scalar function or a virtual-table method. The real signal comes from scenarios 8 and 9.

## macOS's system `sqlite3` cannot load extensions — what that means for the deliverable

`/usr/bin/sqlite3` (shipped with macOS, 3.51.0) is compiled with `SQLITE_OMIT_LOAD_EXTENSION`: the `.load` command does not exist, and neither does the `load_extension()` function (verified here: it fails with `no such function: load_extension`). The whole probe therefore loaded the cdylib into `/opt/homebrew/opt/sqlite/bin/sqlite3` (3.53.0) instead.

Spec §3 already fixes v0's form as "a SQLite loadable extension (Rust cdylib)" and states that it does not cover browsers or the iOS system SQLite. This adds a fact of the same kind: **Apple's own macOS system sqlite3 CLI cannot host ivmlite either**. That does not change the choice of form for v0 — a cdylib is still the right form, and the claim that it covers server, desktop and CLI still holds — but it means:

1. **The "easy to try from the CLI" demo path cannot use the stock `sqlite3` on macOS.** Users need the Homebrew build (or any build not shipped by Apple that leaves extension loading enabled). That is a documentation and onboarding pitfall to state clearly, not an architectural problem.
2. Most language bindings (Python's `sqlite3` module, `rusqlite` itself, DB Browser for SQLite, and so on) do not link Apple's system libsqlite3 and leave extension loading enabled by default, so the "embedded in an application" path is unaffected.
3. The fact **does not require changing §3**; it is a supplementary note. The user documentation / README should say up front: "if you use the stock sqlite3 CLI on macOS, `.load` fails — use the Homebrew build."

## Decision

**Design B is green on every scenario that applies to it** (scenario 8 does not apply to B, by the matrix's definition). By the probe document's decision rule: "B all green → adopt B; §8.3 is settled, and the control-surface syntax is fixed as `CREATE VIRTUAL TABLE ... USING ivm(...)`".

Design A is not all green: scenario 8's self-referential write is a serious, silent resource-exhaustion failure, and scenario 9's dangling trigger leaves the user's base table unwritable, with no teardown API that SQLite drives in the right order the way it drives `xDestroy`. Neither is **decisive** (the only outcome in the decision rules that says "stop and do not enter M1" is both designs having problems, which is not the case here), but together they confirm the "still choose B" tier: even setting A's problems aside, B's three structural advantages (DDL happens in the context designed for it, the view is a real object `sqlite_master` knows, `DROP TABLE` cleans up naturally through `xDestroy`) still hold, and the scenario 8/9 measurements only strengthen the evidence for that choice.

**A is recorded as the fallback but not recommended for v0**: if some future reason forces a move back to scalar UDFs, the two pitfalls from scenarios 8 and 9 must be solved first — scenario 9 needs an explicit teardown API with a guaranteed call order, and scenario 8 needs the self-referential shape ("calling refresh from a statement that scans the target shadow table") to be forbidden explicitly, in the documentation or at runtime, or it will hit the unbounded loop measured here.

## Loose ends

- Scenario 8's "structurally not exposed" claim for B is an argument, not a measurement — the matrix defines scenario 8 as A only, and it is labelled accordingly.
- The two-connection scenarios (6/7) did not test three or more connections; the matrix did not ask for it, and it was not done.
- Scenarios 6/7 in WAL mode were run once each, not repeatedly to look for an occasional timing window (for instance a WAL checkpoint interleaving with a control-surface call). The matrix did not ask for that granularity; recorded as untested.
- Scenario 8 sub-case two was interrupted by hand at 464,538 rows rather than run until memory or disk was exhausted. The runaway pattern — no error, no slowdown, linear growth — was already fully established, and running further would only have confirmed the same thing.
