# Five additional demand-shaped rollups

Measured on 2026-10-15 using commit `1c61d6e`, with the release
`0.1.0-alpha.4` extension. Machine: Apple M2 Pro, 16 GiB RAM. The raw files
record the operating system, SQLite version, checked extension path, source
revision, load averages, wall time and exit status.

These are synthetic in-memory fixtures adapted from the public reports;
upstream timings are not before/after measurements of ivmlite. Runs execute
sequentially in Zenod, Nicti, Postio, Phoenix, PocketBase order. Each uses
three repeats, rotating five modes, with one warm-up and ten measured mixed
batches per mode/repeat. Every row reports a median over repeats of each
run's median batch total; component medians are not summed.

The comparison includes the writes, maintenance and full result read. It
uses the faster of ordinary recomputation and covering-index recomputation.
Phoenix's covering mode explicitly names both indexes; its ordinary mode
uses the planner's natural choice. The trigger baseline uses independent
local SQL triggers generated from fixed case definitions, not upstream
application code. None of the tests demonstrates production adoption.

Correctness checks cover SQLite multiset oracles, mixed writes, explicit
refresh visibility, a second refresh with no new writes, zero sums, vanished
groups, and both sides of joins including parent rekeys and orphan rows.
The indexed query's equivalence is checked after all timed rounds and space
sampling. The covering-plan regression was also checked by mutation: the
old "any covering index" condition makes the partial-coverage test fail;
restoring the all-relations condition passes.

## Results

All times are milliseconds per mixed batch, including writes, maintenance
and draining the complete result. All five runs exited successfully.

| Case | Initial scale | Operations/batch | Faster recompute | Local SQL triggers | ivmlite | Recompute / ivmlite |
|---|---:|---:|---:|---:|---:|---:|
| [Zenod](2026-10-15-zenod-m2pro.txt) | 1,760,000 ledger events | 200 | 95.347 | 1.593 | 2.817 | 33.85x |
| [Nicti](2026-10-15-nicti-m2pro.txt) | 2,000,000 assets; 2 memberships/asset | 200 | 2,847.376 | 2.508 | 8.101 | 351.48x |
| [Postio](2026-10-15-postio-m2pro.txt) | 81,000 messages | 200 | 1.997 | 1.076 | 1.913 | 1.04x |
| [Phoenix](2026-10-15-phoenix-m2pro.txt) | 4,952,148 spans | 200 | 1,788.722 | 3.309 | 8.702 | 205.55x |
| [PocketBase](2026-10-15-pocketbase-m2pro.txt) | 18,000 books | 40 | 1.069 | 0.393 | 1.678 | 0.64x |

Nicti uses ordinary recomputation (including its base-schema join-key index)
as the faster baseline; all other cases use covering-index recomputation.
A ratio below 1 means ivmlite is slower. Postio is approximately tied at
this scale, and PocketBase is slower; neither is evidence that the source
application should adopt ivmlite. The local SQL triggers are faster in all
five cases. These are aggregate-relation measurements, not API timings or
measurements of each upstream implementation.

## Refresh, startup and space

| Case | ivmlite writes | Refresh | Read | Bootstrap | Base SQLite KiB | ivmlite SQLite KiB | Space / base |
|---|---:|---:|---:|---:|---:|---:|---:|
| Zenod | 1.648 | 1.116 | 0.062 | 1,066.544 | 32,936 | 33,104 | 1.01x |
| Nicti | 2.501 | 5.337 | 0.229 | 25,351.129 | 180,052 | 885,736 | 4.92x |
| Postio | 1.619 | 0.283 | 0.012 | 46.044 | 1,136 | 1,236 | 1.09x |
| Phoenix | 1.998 | 6.394 | 0.129 | 22,632.161 | 157,596 | 885,672 | 5.62x |
| PocketBase | 0.297 | 0.447 | 0.912 | 30.293 | 344 | 1,396 | 4.06x |

The component columns are separate medians and must not be added to recreate
the total. Bootstrap is a one-time cost outside the batch totals. SQLite KiB
is the in-memory page allocation, not process RSS, peak memory or on-disk
file size. In particular, the join workloads require about 25.4/22.6 seconds
to bootstrap and about 4.92/5.62 times their base SQLite allocation for
Nicti/Phoenix, respectively. Those are material costs even when repeated
refreshes are much faster than recomputation.

PocketBase reads over 5,000 result groups, so its 0.912 ms result scan is a
large part of the 1.678 ms total. This benchmark does not time an individual
author lookup, the PocketBase API, or a new access path. Zenod and Postio
likewise read the full grouped relation rather than a per-account PK lookup.

The published evidence and exact semantic adaptations are in
[Zenod](../zenod.md), [Nicti](../nicti.md), [Postio](../postio.md),
[Phoenix](../phoenix.md) and [PocketBase](../pocketbase.md).
