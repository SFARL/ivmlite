# Mutation gates: spec requirement → mutation → the test that goes red

## Why this table exists

At the end of M0, the final whole-branch review used **mutation testing** — break the implementation and see whether the tests go red — and, at about one second per run, found three gaps: stubbing the shrinker's legality gate (which spec §9.3 names as the entire reason not to use proptest) to `true` left the whole suite green; deleting the oracle comparison after bootstrap outright left it green; deleting the whole generation loop for the `IsNotNull` predicate left it green.

Before that, **thirteen rounds of reading-based per-task review caught none of them**. Not because the reviewers were careless — the same reviews caught eight substantive problems elsewhere. The difference is method: reading code can judge "is this written correctly", but not "would anyone notice if this were gone".

This table turns the second question into a mechanical check. **Every spec-mandated invariant gets a row** stating what to break and which test goes red. M1's plans require every new invariant to be registered here; a review checks against the table rather than digging through history.

## How to use it

- **When adding a spec-mandated behaviour**, add a row here at the same time, and actually run the mutation once to confirm the test goes red.
- **Only fill the "Verified" column for mutations actually run.** Anything inferred goes in as "unverified". Do not write an inference as a fact — that is the very kind of error this table exists to prevent.
- **A number written into a cell must be read back off the terminal, not computed.** In M1a Phase 2 Task 2 a row said a mutation left the suite "all green (134/134)", when it was actually 128/128 — and the implementer's own report said 128. Asked where the number came from, the mechanism was specific: six gate rows were being added to this same document at the time, the row count and the test count got conflated, 128 + 6 = 134 was computed, and that **computed** number was then written down as an observed fact. It was not a typo (there was no correct 134 to mis-copy), nor a labelled estimate. A number never observed, sitting in a document whose whole purpose is "make claims mechanically checkable", is exactly what the document is meant to prevent. The counting script cannot catch this class — it counts row classifications, not the numbers embedded in cells.
- After a mutation, **always confirm the code still compiles**. This has bitten once: an injected mutation had a syntax error, `grep` filtered out the compile error, and "no output" looked exactly like "tests passed" — an empty verification nearly got recorded as a valid one.
- The full suite runs in about 1.5 seconds (after the first build). Mutation verification is cheap; do not skip it because "running the tests is expensive" — **that assumption has already been wrong once**, and it made thirteen rounds of review give up the most effective tool they had.
- **Use `cargo test --workspace --locked --no-fail-fast`.** The default `cargo test --workspace` stops after the first crate that fails, and crates are built in dependency order — so a test in a downstream crate that a mutation happens to affect goes red first and masks the real target. Measured: after changing `validate`'s `>` to `>=`, the default command showed only `cells_reproduce_exactly_the_published_csv_matrix` red, and the guard test the row names, `base_rows_equal_to_group_cardinality_is_accepted`, never ran.
  This masking is **far more dangerous than "nothing went red"**: something really did go red, so an auditor marks the row verified on the strength of a test the table does not name. It passes itself off as success.

M1b's SQLite shadow-table implementation does not inherit this guard: it must decide for itself whether "leaving zombie state behind after emptying" exists in a `DELETE`-based implementation (very likely not — SQL `DELETE` has no notion of an "empty shell container"), and if it does, write an equivalent test of its own, rather than assuming it is fine because `MemArrangement` was "verified".

The `ivmlite-core` row for replacing `refresh`'s per-table merge `BTreeMap` with a `HashMap` (added in M1a Phase 2 Task 6) — with one table, `by_table` has one key and order is meaningless; with several, the advance order in `for (table, delta) in &by_table` currently affects only the order of `self.view.merge(...)` calls, and `ZSet::merge` is pointwise addition, independent of call order, so no observation point can currently see this order, as measurement confirmed (163/163 green). Once join lands, the `ΔR⋈ΔS` term reads both sides' arrangements' current state, and the order of the two sides' `apply` / `refresh` affects the output for the first time — at which point this mutation must be re-run, confirmed to turn red, and "n/a" changed to "verified".

**The second item is more dangerous than the first**, which is why it is listed separately: `bases` is not the internal state of some engine under test, it is the oracle input fed straight into `recompute_via_sqlite`. If only the first item (the engine side) were re-verified and the second missed, then after join lands the harness could route deltas to the engine correctly (the table names and raw deltas `apply` receives are right) while the `bases` map fed to the oracle had its non-anchor tables frozen at their bootstrap state; the oracle would then compute `ΔR⋈S` against a stale `S` and get an equally wrong `want`. That is not "the engine was wrong and went undetected" but **both sides of the comparison wrong, and wrong the same way**: `got == want` would still hold, `run` would still return `Ok`, and this is the one place in the whole suite where "the oracle itself lies" with no mechanism able to expose it.

**At that point items 1, 2, 3, 4, 5a and 6 must all have their mutations re-run** (final review Finding F: this closing instruction used to list only "items 1, 2, 3 and 4a", with neither item four (then still a dangling reference; see the note on item 4 above) nor item five (the numbering then; item 6 now) — even though item 6's own description says plainly "at that point this mutation must be re-run". This is the operational instruction that "does not depend on anyone remembering", and an omission from it is as good as not writing it), confirming one by one that each now really makes a test go red, and only then changing the row's "n/a" to "verified". The second item above all must not be skipped — it checks not whether some component under test is correct, but whether the judge of the components still stands. Item 5a likewise cannot be replaced by "the trait's own unit tests were already green" — the unit tests prove that `MemArrangement`'s implementation is right, not that the join operator correctly depends on the trait (it might, say, keep state in a local variable by mistake and bypass the `Arrangement` interface). Item 6 cannot be skipped as "irrelevant with one table" — once join lands, single-table cases are no longer the only shape of case.

**Item 5b is not part of that re-verification**, for the reason in 5b's own description: it tests a private field of `MemArrangement`, and re-running the mutation does not make it verifiable just because join now uses `Arrangement` — this item should not, and cannot, be covered by the act of "re-verifying". Its "n/a" stays "n/a" until M1b decides whether the SQLite shadow-table implementation needs an equivalent test of its own; if it does, that is a new row in M1b's own task, not a change to this row's status. This closing checklist lives in this document, so it does not depend on anyone remembering.
