# Mutation gates: spec requirement → mutation → the test that goes red

## Why this table exists

At the end of M0, the final whole-branch review used **mutation testing** — break the implementation and see whether the tests go red — and, at about one second per run, found three gaps: stubbing the shrinker's legality gate (which spec §9.3 names as the entire reason not to use proptest) to `true` left the whole suite green; deleting the oracle comparison after bootstrap outright left it green; deleting the whole generation loop for the `IsNotNull` predicate left it green.

Before that, **thirteen rounds of reading-based per-task review caught none of them**. Not because the reviewers were careless — the same reviews caught eight substantive problems elsewhere. The difference is method: reading code can judge "is this written correctly", but not "would anyone notice if this were gone".

This table turns the second question into a mechanical check. **Every spec-mandated invariant gets a row** stating what to break and which test goes red. M1's plans require every new invariant to be registered here; a review checks against the table rather than digging through history.

## How to use it

- **When adding a spec-mandated behaviour**, add a row here at the same time, and actually run the mutation once to confirm the test goes red.
- **Only fill the "Verified" column for mutations actually run.** Anything inferred goes in as "unverified". Do not write an inference as a fact — that is the very kind of error this table exists to prevent.
- **A number written into a cell must be read back off the terminal, not computed.** In M1a Phase 2 Task 2 a row said a mutation left the suite "all green (134/134)", when it was actually 128/128 — and the implementer's own report said 128. Asked where the number came from, the mechanism was specific: six gate rows were being added to this same document at the time, the row count and the test count got conflated, 128 + 6 = 134 was computed, and that **computed** number was then written down as an observed fact. It was not a typo (there was no correct 134 to mis-copy), nor a labelled estimate. A number never observed, sitting in a document whose whole purpose is "make claims mechanically checkable", is exactly what the document is meant to prevent. The counting script cannot catch this class — it counts row classifications, not the numbers embedded in cells.
- After a mutation, **always confirm the code still compiles**. This has bitten once: an injected mutation had a syntax error, `grep` filtered out the compile error, and "no output" looked exactly like "tests passed" — an empty verification nearly got recorded as a valid one.
- The full suite runs in about 1.5 seconds (after the first build). Mutation verification is cheap; do not skip it because "running the tests is expensive" — **that assumption has already been wrong once**, and it made thirteen rounds of review give up the most effective tool they had.
- **Use `scripts/test-all.sh`, not a bare `cargo test`.** (M1b Phase 3a, Task 5.) It builds the extension first, then runs the extension's own unit tests, then runs `cargo test --workspace --locked --no-fail-fast` — so a mutation in `ivmlite-core`, `ivmlite-sql` or `ivmlite-sqlite` itself reaches the extension tests too. Without the rebuild, those tests load a stale library and fail with an instruction to rebuild rather than with the mutation's real symptom, which is not the same thing as going red for the reason a row names. **Sum `passed`/`failed` over every test binary of both cargo invocations the script makes.** A run takes about 40 seconds. The script itself runs both invocations unconditionally and reports a combined failure only at the end — it does not stop after the extension's own tests the way a plain `set -e` script would, precisely so a mutation that only the extension can see does not truncate the workspace run and leave the gate count incomplete.
  **Use `--no-fail-fast` on the workspace invocation.** The default `cargo test --workspace` stops after the first crate that fails, and crates are built in dependency order — so a test in a downstream crate that a mutation happens to affect goes red first and masks the real target. Measured: after changing `validate`'s `>` to `>=`, the default command showed only `cells_reproduce_exactly_the_published_csv_matrix` red, and the guard test the row names, `base_rows_equal_to_group_cardinality_is_accepted`, never ran.
  This masking is **far more dangerous than "nothing went red"**: something really did go red, so an auditor marks the row verified on the strength of a test the table does not name. It passes itself off as success.
- **A row's red set is valid as of its last measurement, not forever.** Several `ivmlite-core` rows below were written when the differential enumerator (`crates/ivmlite-test/src/query.rs`) generated only `Compare{op: Gt}` and no `IsNull`/`Ge`/`Ne`/etc.; their recorded red sets said things like "the only one that goes red: `enumerate` never generates `Ge`". M1b Phase 2a Task 2 then widened the enumerator to the whole predicate whitelist, and those claims went stale without anyone touching the rows — a mutation the final review re-ran (`matches` requiring `ColumnType::Integer`) came back 231 passed / 6 failed where the table still said 232 passed / 1 failed. **Any change to the enumerated query space (`enumerate`, `enumerate_join`, `enumerate_database`, or what they call) means re-running every row whose red set names or excludes one of the differential sweeps**, not just the rows the change was made for — the sweeps' red sets are a consequence of what they happen to generate, and that can change underneath a row that never touched the mutated code.

**The second item is more dangerous than the first**, which is why it is listed separately: `bases` is not the internal state of some engine under test, it is the oracle input fed straight into `recompute_via_sqlite`. If only the first item (the engine side) were re-verified and the second missed, then with a join the harness could route deltas to the engine correctly (the table names and raw deltas `apply` receives are right) while the `bases` map fed to the oracle had its non-anchor tables frozen at their bootstrap state; the oracle would then compute `ΔR⋈S` against a stale `S` and get an equally wrong `want`. That is not "the engine was wrong and went undetected" but **both sides of the comparison wrong, and wrong the same way**: `got == want` would still hold, `run` would still return `Ok`, and this is the one place in the whole suite where "the oracle itself lies" with no mechanism able to expose it.

Measured in M1a Phase 3 Task 5, the danger is real and precise: item 2's mutation alone is caught, because the engine under test is right and the stale oracle disagrees with it; but with the reference engine making the same mistake (items 1 and 2 together), every `NaiveRecompute`-driven join test stays green, and only the tests whose subject is `IncrementalEngine` — which keeps its own join state — go red. This remains true of any future multi-table shape: an oracle-side bookkeeping error is caught only by an engine that does not share it, so a change to how `run` maintains `bases` must be re-verified against an independent engine, not the reference one. The final review found a second instance of the same shape: reading the right table's join key at `left_column` in both `NaiveRecompute` and the oracle's `ON` clause is caught only by the `IncrementalEngine` sweep over the swapped database (see the key-position row in "semantic contracts").
