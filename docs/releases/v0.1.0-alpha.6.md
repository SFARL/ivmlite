# ivmlite v0.1.0-alpha.6

Release date: 2026-10-20.

The sixth technical preview of ivmlite, an experimental
SQLite loadable extension for incrementally maintained grouped aggregates.
This version accepts existing non-STRICT tables and all SQLite storage classes,
and adds exact REAL aggregation and retractable MIN/MAX.

**Breaking: shadow-table format 6 cannot read alpha.5 format-5 state.** Old views
open as broken views that can be dropped. Drop every old ivmlite view and
recreate it from its SELECT query. There is no automatic migration; keep the
base tables and the view definitions as the source of truth.

## What changed

- Base tables may be STRICT or non-STRICT, with any declared type interpreted
  by SQLite affinity. STRICT ANY is accepted. NULL, INTEGER, REAL, TEXT and
  BLOB pass through capture, state and output without storage-class coercion.
- `COUNT(column)`, `TOTAL(column)`, `AVG(column)`, `MIN(column)` and `MAX(column)`
  join `COUNT(*)` and `SUM(column)`. SUM accepts any column, including SQLite's
  numeric classification of TEXT and BLOB values. Extremum state retains live
  multiplicities and survives retractions.
- REAL and BLOB comparison literals are accepted. Literal conversion follows
  comparison affinity, except REAL against TEXT-affinity columns is refused:
  SQLite REAL-to-TEXT rendering varies by version, so use a quoted string.
- Join columns must have the same affinity. Canonical numeric key equality
  makes INTEGER 1 match REAL 1.0; NULL still matches nothing. Group keys use
  the same equality, and output REAL when any live key in the group is REAL.
- FluxFlow's adapted demo uses native REAL amounts; Kener uses REAL latency
  and AVG/MIN/MAX. Their stored buckets and reader-side work still apply.
- Widened mixed-type differential tests compare both the real extension and
  in-memory engines with SQLite and an independent exact reference. Additional
  tests exercise order independence, persisted extremum multiplicities, and
  the actual artifact's new features across refresh, rollback and reopen.

## Differences from SQLite

REAL SUM, TOTAL and AVG return the exact result rounded once. SQLite uses
scan-order Kahan–Babuška–Neumaier summation and divides after rounding its sum,
so last bits may differ: AVG of 0.1, 0.2 and 0.3 is `0.2` in ivmlite and
`0.19999999999999998` in SQLite. Finite inputs can also overflow SQLite's
intermediate accumulator to infinity, or produce NULL after intermediate
infinity cancellation, while ivmlite's exact final result is finite. The
finite-input fixtures observe infinity on bundled SQLite 3.53.2; synthetic
comparator tests cover NULL compatibility separately. Actual +Inf and -Inf
inputs together return NULL, as in SQLite.

Integer SUM fails refresh with `integer overflow in SUM` only when the final
exact result is outside signed 64-bit range. SQLite can fail when a prefix of
its scan overflows even if the final exact result fits. MIN returns INTEGER
and MAX REAL for numerically equal INTEGER/REAL inputs; SQLite's choice
depends on scan order.

## Workload compatibility

The [After M2c census](../census/2026-10-17/README.md#after-m2c) projects ten of
28 application candidates as compatible after their documented adaptations:
four high-confidence and six low-confidence fits. It does not demonstrate
upstream execution, adoption or speedups. M2c alone unlocks no Nexmark query as
written; the hypothetical nine-query bundle still requires non-aggregate
views, SELECT expressions and a richer WHERE.

## Task 13 application measurements

The [M2c benchmark results](../bench/README.md#m2c-column-types-and-aggregates)
cover native macOS ARM64 runs on October 19–20: 100 ablation, 240 confirmation,
92 demo and 48 write-amplification rows, plus one 40-row confirmation follow-up.
All original ivmlite steady integer ratios are at most 1.038; the eight
unchanged integer demos' maximum is 1.0367. The original naive-recompute
maintenance/combined flags of 1.061/1.062 did not reproduce in the single
follow-up (1.027/1.028). The follow-up's new trigger-control combined flag is
1.053, versus 1.022 originally; it remains reported and no further rerun was
chosen. The original flags do not establish a persistent regression, and no
spec waiver is needed. This does not mean every raw comparison is below 5%.
The host was not isolated, limiting small-effect attribution.

FluxFlow's native REAL amounts and Kener's AVG/MIN/MAX query change the work
being measured. Current combined costs are 6.052 versus 135.890 ms for
FluxFlow's indexed recomputation, and 11.072 versus 572.612 ms for Kener;
Kener's full-result read raises ivmlite end-to-end cost to 166.546 ms. Its
bootstrap costs 30,638.833 ms, and database page allocation is 1,760,784 KiB
versus 255,436 KiB for the same-day old integer query (6.893x). This allocation
includes base tables and database structures, not RSS or pure operator state.
The [FluxFlow](../demos/fluxflow.md#m2c-source-scale-result-2026-10-20) and
[Kener](../demos/kener.md#m2c-source-scale-result-2026-10-20) pages retain full
ranges, indexed/unindexed comparisons, trigger limitations and historical
October 10 alpha.3 tables. Changed-query ratios are not engine speedups or
integer regression checks. These synthetic runs do not establish application
adoption or production performance.

## Known limitations

A nonempty GROUP BY and at least one aggregate are still required. SELECT and
GROUP BY use bare columns; aggregate arguments are bare columns. Views allow
at most one predicate and one two-table inner equi-join. Expressions, AND/OR,
subqueries, CTEs, DISTINCT aggregates, group_concat, HAVING, ORDER BY, LIMIT,
outer/self/multiway joins and retention/sealing remain unsupported. Only
BINARY collation is supported, and the conservative COLLATE check may also
refuse an explicit BINARY declaration. Refresh remains explicit. Supported
SQLite behavior is 3.45 and later; tests use bundled SQLite 3.53.2.

The [parent limitations](../superpowers/specs/2026-09-18-ivmlite-design.md#13-known-limitations-v0)
retain operational boundaries, including host extension availability and
capture restrictions. Workload compatibility is not a promise of an advantage
over indexed recomputation or application-maintained triggers.
