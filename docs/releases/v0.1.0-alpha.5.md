# ivmlite v0.1.0-alpha.5

The fifth technical preview of ivmlite, an experimental SQLite loadable
extension for incrementally maintained grouped aggregates. This release adds
one SQL function that refreshes every view of a database in one call,
either all together or one by one, and makes a refresh with nothing new
almost free.

The shadow-table format is unchanged (5), so databases created with
`v0.1.0-alpha.4` work as they are. The supported SQL is unchanged.

## What changed

- **`ivm_refresh_all()` refreshes every view in one call.** Call it from a
  `SELECT`:

  ```sql
  SELECT ivm_refresh_all();            -- every view or none: 2 refreshed
  SELECT ivm_refresh_all('continue');  -- one by one: refreshed 0, skipped 2, failed 0
  ```

  - **Atomic, the default.** Every view refreshes, or none does. If one view
    fails, everything is rolled back and the call fails with
    `ivm_refresh_all: view <name>: <message>; no view was refreshed`.
    Otherwise it returns the number of views it refreshed, not counting the
    views it skipped because they had nothing new.
  - **Continue.** Each view refreshes on its own. A view that fails is rolled
    back alone, and the result names it with its message, after the counts
    of views refreshed, skipped and failed.
  - **Where to call it.** From a statement that writes, it fails with a
    message saying so. SQLite refuses it in the database schema's triggers,
    views and `CHECK` constraints. Inside your own `BEGIN … COMMIT` it
    works, and a later `ROLLBACK` undoes it.
  - **Waiting for other writers.** In autocommit it starts with
    `BEGIN IMMEDIATE`, so it waits for another connection's write lock under
    `busy_timeout`, as a refresh statement does. Called as
    `SELECT ivm_refresh_all() FROM t`, whose read is already under way, it
    cannot wait and fails with `database is locked`. Inside your own
    transaction, start it with `BEGIN IMMEDIATE` to wait.
  - **Failures that end the transaction.** A failure that rolls back the
    whole transaction, such as a trigger's `RAISE(ROLLBACK)`, fails the call
    in either mode, and ends your own transaction if it ran inside one.

  A view's own refresh, `INSERT INTO v(v) VALUES ('refresh')`, is itself a
  write, and SQLite cannot open a savepoint inside one. So a function called
  from a `SELECT` is the only way to make several views' refreshes atomic
  together.
- **A refresh with nothing new returns early.** If no base table has a
  change past a view's last refresh, the refresh stops after its checks. It
  computes, stages and applies nothing. This helps every refresh, not only
  `ivm_refresh_all`. The checks always run first. A base table that was
  dropped and recreated has lost its capture triggers, so its changes are no
  longer recorded. The checks are what report that view as broken; a
  shortcut around them would leave it silently out of date.

## What the benchmark found

The full results, data and reproduce commands are in
[docs/bench/README.md](https://github.com/SFARL/ivmlite/blob/v0.1.0-alpha.5/docs/bench/README.md),
"M1b Phase 7". They come from a new Python driver, separate from the matrix,
which times a refresh of every view over 100,000 base rows in 1,000 groups.
In short:

- **`ivm_refresh_all` is not faster than your own loop.** Against a loop of
  refresh statements the application keeps prepared, it costs 4.0–5.4 µs more
  per view per call with one-row or empty batches: 8.97 against 8.16 ms for
  200 views (1.10x), and twice the loop's time when every view is idle. The
  reason is that it prepares its nested statements on every call. A cached
  statement that names an ivmlite view would keep the connection from
  closing, so the function may not keep them. With 1,000-row batches it read
  2–4% faster than the loop, within the run's ranges. Use it for the
  atomicity and the single call, not for speed.
- **An idle refresh is about 4x cheaper.** Refreshing 200 views with nothing
  new now takes 0.87 ms instead of 3.75 ms, about 4.3 instead of 18.7 µs per
  view. With half the views idle, refreshing all 200 is 1.33x faster (in every
  round, with overlapping ranges).
- **Nothing else moved.** Where every view has new changes, both builds do
  the same work, and the loop timings stayed within 0.97–1.02x of the
  previous release.

Known limitations:

- `ivm_refresh_all` refreshes every view of the database. It cannot refresh
  a chosen subset, or only the views that read one table.
- Each view still reads its own changes. Views over the same table do not
  share one read of it.
- The limitations of `v0.1.0-alpha.4` still apply: refresh and writes are
  still several times slower than hand-written triggers, reconnecting many
  views at once is still slow, and each open view keeps about 40 KB of cached
  statements.

These numbers come from in-memory databases with uniformly distributed data,
measured through Python's `sqlite3` on a machine that was not fully idle.
Real workloads will differ; reports of real schemas and queries, including
ones ivmlite rejects or makes slower, are the most useful feedback.
