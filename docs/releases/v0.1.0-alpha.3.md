# ivmlite v0.1.0-alpha.3

The third technical preview of ivmlite, an experimental SQLite loadable
extension for incrementally maintained grouped aggregates. This release makes
refresh cheaper, and measures each change against alpha.2 with the same
protocol as before.

**Correction (2026-10-10).** These notes first said that the Kener demo's
steady-state refresh got slower than in alpha.2, by 0.80x to 0.90x. That was
wrong. The demo benchmark timed one refresh per repeat, which is too noisy to
resolve a change of that size. It now times ten steady-state batches per run,
and with it Kener's refresh is 1.24x faster than in alpha.2 (2.772 → 2.235 ms
median), and steady-state refresh is 1.14–1.45x faster in all four demos. The
corrected results are in the "M1b Phase 5" section of
[docs/bench/README.md](https://github.com/SFARL/ivmlite/blob/55f1cb9/docs/bench/README.md).
The release's code is unchanged.

**Breaking: the shadow-table format is now 4.** Views created with
`v0.1.0-alpha.2` report a format error on every read and refresh. They still
open as broken views, so `DROP TABLE <view>` works with this release loaded;
drop every alpha.2 view, then create them again. The supported SQL is
unchanged.

## What changed

- **One set-based apply per refresh.** A refresh used to apply its staged
  changes through a trigger that fired once per staged row. It now arms one
  sentinel row, and a trigger fires once and applies the whole stage with
  set-based statements. It is still a single statement, so state, output and
  watermarks still commit together or not at all.
- **No catalog checks on an unchanged schema.** A refresh skips its schema
  checks while SQLite's schema cookie is unchanged. Any schema change, made
  from any connection, makes the next refresh check everything again. At 200
  views and one-row batches, this alone cut refresh by about a third.
- **Smaller new views.** Bootstrap now empties its stage table, so a freshly
  created view no longer holds a second copy of its initial state until its
  first refresh. With 100,000 groups, that about halves the database right
  after `CREATE VIRTUAL TABLE`.
- **Fewer staging statements.** A refresh stages up to 64 rows per
  `INSERT`, within the connection's live limit on SQL variables.
- **New demo benchmarks.** FluxFlow, noop, Zcash and Kener now run through
  one protocol runner, documented with their results in
  [`docs/demos/`](https://github.com/SFARL/ivmlite/blob/v0.1.0-alpha.3/docs/demos/README.md).

## What the benchmark found

The full results, data and reproduce commands are in
[docs/bench/README.md](https://github.com/SFARL/ivmlite/blob/v0.1.0-alpha.3/docs/bench/README.md),
"M1b Phase 5", as published with this tag; its Kener demo finding is
superseded by the correction above. In short:

- in the ablation, write + refresh is 1.35–1.53x faster than alpha.2 in four
  of the five measured configurations, and 3.52x in the fifth (200 views,
  100,000 groups). There, most of the gain is the first refresh after
  `CREATE` no longer draining the bootstrap stage, because the benchmark times
  that first refresh. Steady-state refresh in the demos, measured separately,
  is 1.14–1.45x faster;
- ivmlite beats full recomputation by more than 2x in 57 of the 68 measured
  configurations (alpha.2: 55), including all 48 at 100,000 base rows and
  more. It still loses in the small-table corner (10,000 rows);
- on total write + refresh time it is still far from special-purpose
  hand-written triggers: 1.81x slower at best (10 groups), and 6.64–17.55x
  slower in the other confirmed configurations with batches of 100 or more,
  and thousands of times slower with one-row batches at 200 views. What
  remains is the maintenance itself: writing the state and output tables,
  and running the operator tree;
- in all four demo workloads, steady-state refresh is 1.14–1.45x faster
  (corrected on 2026-10-10; see above). In Kener it is 1.24x faster, while
  its end-to-end time barely moves, because reading its 550,000 groups
  dominates it;
- write cost is unchanged.

These numbers come from in-memory databases with uniformly distributed data
and one refresh per batch, measured on a machine that was not fully idle.
Real workloads will differ; reports of real schemas and queries, including
ones ivmlite rejects or makes slower, are the most useful feedback.
