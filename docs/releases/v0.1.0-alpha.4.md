# ivmlite v0.1.0-alpha.4

The fourth technical preview of ivmlite, an experimental SQLite loadable
extension for incrementally maintained grouped aggregates. This release
removes the fixed costs that every refresh paid, whatever the size of the
change, and changes the benchmark to measure the steady state.

**Breaking: the shadow-table format is now 5.** Views created with
`v0.1.0-alpha.3` report a format error on every read and refresh. They still
open as broken views, so `DROP TABLE <view>` works with this release loaded;
drop every alpha.3 view, then create them again. The supported SQL is
unchanged.

## What changed

- **Statements are compiled once per view.** Each view now keeps the
  statements of its refresh prepared for as long as it is open, instead of
  compiling them on every refresh. Rows are staged in a few fixed statement
  shapes, so a steady refresh prepares nothing, even for a one-row change.
  A statement that a schema change makes stale is prepared again
  automatically, and every refresh still checks the schema first.
- **One catalog read per schema change, per connection.** After any schema
  change, a connection now reads `sqlite_schema` once and shares that snapshot
  among its views, instead of each view making its own lookups. A base
  table's capture checks are computed once and reused by every view that reads
  it. Error messages for broken views are unchanged.
- **Refresh no longer scans every view's progress.** `__ivm_progress` gets an
  index, so the garbage collection in a view's refresh is a search instead of
  a scan over one row per view. This is the format change above. A database
  without that index reports its views as broken; creating any view recreates
  it.
- **The benchmark measures the steady state.** Every benchmark cell now
  applies one warm-up batch and then five measured batches, and reports the
  first refresh separately. Earlier releases timed only the first refresh
  after `CREATE`, which paid one-time costs a later refresh does not; their
  numbers are not directly comparable with this release's.

## What the benchmark found

The full results, data and reproduce commands are in
[docs/bench/README.md](https://github.com/SFARL/ivmlite/blob/v0.1.0-alpha.4/docs/bench/README.md),
"M1b Phase 6". In short:

- with one-row changes, a steady refresh is about 3x faster than in alpha.3:
  at 200 views, from 23.5 to 6.7 ms for all of them (from about 118 to 34 µs
  per view), and at 10 views from 1.12 to 0.37 ms. The first refresh after
  creating 200 views is 9.6x faster (220.6 to 22.9 ms). With batches of 100
  rows or more, refresh time moved by 0.92–1.07x, about the measurement's
  noise floor;
- ivmlite beats full recomputation by more than 2x in 62 of the 68 measured
  configurations, including all 48 at 100,000 base rows and more. It still
  loses in the small-table corner (10,000 rows with 1,000-row batches);
- on total write + refresh time it is still slower than special-purpose
  hand-written triggers: 1.56x at best (10 groups, large batches), and
  6.65–8.01x in the other confirmed configurations. With one-row changes the
  gap is now tens of times, not thousands, and no longer grows with the number
  of views. What remains is the maintenance itself: writing the state and
  output tables, and running the operator tree;
- in the four demo workloads, steady-state refresh is 1.06–1.37x faster,
  and end-to-end time moves by 0.98–1.06x, because each demo refreshes one
  view after a batch of hundreds of rows;
- SQLite's memory use is higher, because each view keeps its statements: about
  40 KB per view, 38.3 to 46.3 MB at 200 views in one probe.

Known limitations:

- Reconnecting many views at once is still slow: about 2.5 s for 200 views
  over 20,000 rows, after a schema change made by another connection or
  rolled back. This predates this release.
- A user's trigger on an internal `__ivm_` table that reads an ivmlite view
  keeps that view's statements alive, so closing the connection returns
  `SQLITE_BUSY`. Triggers on ivmlite's internal tables are not supported.
- Writes to a tracked table still cost more as views are added; the write
  path did not change in this release.

These numbers come from in-memory databases with uniformly distributed data
and one refresh per batch, measured on a machine that was not fully idle.
Real workloads will differ; reports of real schemas and queries, including
ones ivmlite rejects or makes slower, are the most useful feedback.
